# 悟空 - 供应商资质自动核验助手

一个基于 **Vue 3 + Vite + Element Plus + Pinia + Vue Router** 实现的供应商资质自动核验前端项目。

项目严格按照 `需求文档.md` 的边界实现，当前版本为：

- 纯前端 Mock
- 无后端接口
- 不发起真实网络请求
- 供应商端 + 管理员端双角色闭环
- 所有业务数据维护在 Pinia 中

---

## 1. 项目定位

“悟空”面向供应商准入与资质审核流程，目标是把传统人工审核流程数字化、流程化、可追踪化。

当前实现重点覆盖了以下核心链路：

- 供应商注册 / 登录
- 企业信息维护
- 资质文件上传与更新
- 机器预审核验
- 管理员人工复核
- 审核结果同步到供应商侧
- 审核日志留痕
- 审核标准模板管理
- 供应商文件更新监控

## 3. 当前实现内容

### 3.1 供应商端

- 登录 / 注册页
- 企业信息管理页
- 文件管理
- 我的核验记录
- 核验详情页
- 帮助中心

已实现能力：

- Mock 账号密码登录
- 注册短信验证码校验
- 忘记密码与手机号验证码重置
- 注册时录入企业基础信息
- 企业信息实时校验
- 工商 Mock 数据比对
- 资质文件类型、大小校验
- 防重复上传
- 即将过期 / 已过期文件提醒
- 文件更新窗口
- 上传后自动进入“审核中”
- 自动生成机器识别字段
- 自动生成标准字段比对结果
- 自动生成风险标记
- 自动生成预审评分
- 支持未通过记录重新上传
- 支持需更新文件集中处理
- 支持 PDF / 图片在线预览

### 3.2 管理员端

- 管理员登录页
- 待审核文件列表
- 审核详情工作台
- 供应商管理列表
- 审核标准管理页
- 审核日志页

已实现能力：

- Mock 管理员账号登录
- 查看全部审核记录
- 按状态 / 类型 / 时间 / 关键词筛选
- 查看文件预审结果和比对详情
- 查看供应商文件更新监控
- 执行人工审核并填写意见
- 审核通过后锁定记录
- 审核未通过后要求供应商重新上传
- 查看供应商档案、上传记录、变更历史
- 管理审核模板、门槛分、权重和一票否决项
- 导出 Mock 审核日志

### 3.3 规则与状态流转

已实现的核心状态规则：

- 上传完成后自动进入 `审核中`
- 管理员审核通过后进入 `已通过`
- `已通过` 记录锁定，不允许再次审核
- 管理员审核未通过后进入 `未通过`
- 未通过记录只能通过重新上传进入下一轮审核
- 管理员不能修改供应商原始资料
- 企业信息变更不覆盖历史审核记录

### 3.4 机器预审 Mock 能力

当前前端内置了一个简化版“机器预审”逻辑，依据文件名和类型模拟以下能力：

- 证书有效期检查
- 字段识别结果生成
- 标准字段比对
- 风险标签生成
- 同源主体命中
- 评分计算
- 一票否决规则判断

说明：

当前不是 OCR/NLP 真识别，而是前端规则模拟。这样做是为了符合“纯前端 Mock、无后端接口”的要求。

## 8. 当前数据说明

当前版本所有业务数据都保存在 Pinia 内存状态中，包括：

- 登录态
- 供应商基础信息
- Mock 工商数据
- 文件记录
- 机器预审结果
- 审核意见
- 审核日志
- 标准模板
- 文件更新状态

这意味着：

- 页面刷新后会恢复到初始 Mock 数据
- 新增注册、上传、审核结果不会跨刷新保留
- 文件预览基于当前浏览器会话的对象 URL 或内置 data URI

## 10. 我建议下一步优先补的功能

如果继续迭代，这几个功能最值得优先加：

### 10.1 本地持久化

建议把 Pinia 状态接到 `localStorage` 或 IndexedDB。

价值：

- 刷新页面后数据不丢
- 更接近真实系统体验
- 便于验收和演示

### 10.2 分页与排序补齐

需求文档里明确提到“列表分页、排序、搜索、筛选”，当前项目已实现搜索和筛选，但分页、排序还可以补得更完整。

建议增加：

- 表格分页器
- 上传时间排序
- 预审分排序
- 审核状态排序

### 10.3 多级审核流

目前是单管理员审核。文档里提到支持“多级审核 / 会审”，后续可以增加：

- 初审
- 复审
- 会审
- 驳回重提

### 10.4 审核报告生成

可以在审核完成后生成一份结构化报告：

- 企业基础信息
- 文件清单
- 风险项
- 评分详情
- 审核结论
- 改进建议

### 10.5 复评提醒中心

文档中要求默认 5 年复评提醒。前端 Mock 可先做：

- 到期日计算
- 即将到期列表
- 首页提醒卡片
- 管理员待办提醒

### 10.6 申诉与复核

未通过后，供应商除了重新上传，也可以：

- 发起申诉
- 提交补充说明
- 指定复核人
- 留存复核结论

## 11. 我看到的逻辑边界和可优化点

这部分不是“报错”，而是当前版本如果继续做产品化，建议尽快处理的地方。

### 11.1 刷新即丢数据

这是当前最大边界。

原因：

- 状态全在内存 Pinia 中
- 没有本地持久化

影响：

- 演示时容易误以为“系统没保存”
- 不利于多轮审核验证

### 11.2 上传去重规则目前偏严格

当前逻辑是：

- 同一供应商同一类型文件，如果已有 `审核中` 或 `已通过` 记录，则禁止再次上传

这个逻辑符合文档里的“防重复上传”，但在真实业务里通常还要区分：

- 是否允许上传新版本
- 是否允许多个“其他资质”
- 是否允许保留多历史版本但仅一个生效版本

后续建议把“重复上传”升级成“版本管理”。

### 11.3 文件更新已有闭环，但还不是完整版本管理

当前已经支持：

- 识别即将过期文件
- 识别已过期文件
- 识别未通过待更新文件
- 供应商侧更新窗口
- 管理员侧同步监控

真实业务里还可以继续扩展：

- 每类资质的当前生效版本
- 历史版本对比
- 新旧文件差异说明
- 管理员催办记录
- 更新截止时间

### 11.4 机器预审依赖文件名规则模拟

现在是前端 Mock，所以像“过期”“不一致”“技术不足”这类风险来自文件名规则。

这对演示是够的，但如果后续继续扩展，建议把这层逻辑抽成独立规则引擎模块，避免 store 里业务越来越重。

### 11.5 日志导出是 Excel 兼容 CSV

当前导出采用 CSV 方式，Excel 可以直接打开，但它不是严格意义上的 `.xlsx` 文件。

这样做的原因是：

- 避免引入更重的依赖
- 保持项目轻量

如果后续要正式交付给业务方，建议补成真正的 `.xlsx` 导出。

### 11.6 文件预览属于会话级 Mock

当前新上传文件的预览依赖浏览器对象 URL。

这意味着：

- 当前会话内可预览
- 页面刷新后对象 URL 会失效

如果要提升演示完整度，建议把文件转为 base64 或接入浏览器本地存储。

### 11.7 标准模板和评分规则还可以继续细化

当前已经支持：

- 模板
- 门槛分
- 权重
- 一票否决

但还没有细分到每个审核指标项，比如：

- 质保维度下的具体子项打分
- 技术维度下的设备/检验/工艺分项
- 商务维度下的财务/运输/售后分项

这部分如果补齐，审核工作台会更贴近真实业务。
